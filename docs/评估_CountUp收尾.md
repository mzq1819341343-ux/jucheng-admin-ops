# 评估 · CountUp 收尾（指令69 A5，只评估未开发）

> 背景：指令68-P1-T1 以 (b) 改良形把总览英雄数字改为终值直出后，
> CountUp 的最后一处启用也随之关闭。本评估盘点其现状与去留，
> **本轮不删、不改**，等督工裁定。

## 现状盘点（代码实查）

- `components/CountUp.tsx`（59 行，"use client"）：把已格式化的展示
  字符串中的数字从 0 滚动到目标值；SSR/首帧先渲染终值，挂载后才
  滚动；尊重 `prefers-reduced-motion`；实现本身无缺陷。
- 唯一导入方是 `components/KpiCard.tsx`：`KpiValue` 的 `animate`
  属性为真时才渲染 `<CountUp duration={450}/>`，`KpiCard` 再以
  `countUp` 属性透传。全仓检索（app/ + components/）：
  **`countUp=` 与 `animate=` 的传参调用为 0 处**——所有 KPI 渲染
  均走默认静态路径。
- 结论：组件 + 两层属性接口构成一条完整但**无调用方的死链**，
  仅靠默认值关着；因 `animate` 是运行时条件分支，打包器无法
  摇树剔除，CountUp 代码仍随 KpiCard 进入相关页面的客户端包。

## 删除 vs 保留

| 维度 | 删除（组件 + animate/countUp 接口） | 保留现状 |
|---|---|---|
| 功能影响 | 无：零调用方，当前所有数字本就静态渲染，回归锚点不受影响 | 无 |
| 代码面 | −59 行组件、KpiCard 去两层属性与一处 import，KPI 接口回到单一静态语义 | 维持 137 行（KpiCard+CountUp）双语义接口 |
| 风险 | 未来若真需要滚动数字（如非首屏的展示型大数），需重写——但实现仅 59 行且方案已在本仓文档留痕（62-A5/63-A3/68-T1），重写成本低 | **误用风险**：后来者见现成接口，可能顺手给首屏/LCP 元素重新开启，正是 T1 刚消除的双簇钉点成因；防误用只能靠注释自觉 |
| 观感 | 无变化（现在就没有滚动） | 无变化 |

## 结论（等裁定）

倾向**删除**：零调用、其唯一历史用途（首屏英雄滚动）已被裁定为
LCP 钉点成因而移除、重写成本有据可查——留着的主要价值（现成
可用）恰与主要风险（现成误用）同源。若督工倾向保留，备选是给
`KpiCard.tsx` 与 `CountUp.tsx` 文件头各补一行硬警告「不得用于
首屏/LCP 元素（见 68-T1）」，把口头教训钉进代码注释；两案均等
裁定后另笔执行，本轮未动代码。
