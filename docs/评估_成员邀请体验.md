# 评估 · 成员邀请体验（指令58 A7，只评估不开发）

> 结论先行：推荐立项做「待邀请名单 + 一键对齐」（一期），预计工时 4–5 小时，
> 能把老板侧每邀请一人从「3 个界面约 6 步」压到「2 个界面 3 步」，且不引入
> service-role 密钥、不改现有 RLS 边界。是否立项等老板裁定，本文件不含开发。

## 一、现状（Supabase 控制台流）

邀请一个成员并使其按正确角色/授权登录，老板侧全流程：

| 步 | 界面 | 动作 |
|----|------|------|
| 1 | Supabase 控制台 → Authentication → Users | 填邮箱发邀请（或手动建号） |
| 2 | （对方侧）邮箱 | 点邀请链接 → /auth/set-password 设密码（约 2 分钟） |
| 3 | Supabase 控制台 → Table Editor → profiles | 找到该用户行，改 role 与 store_scope（默认 staff） |
| 4 | 本站 /members | 逐个勾选业务板块授权（勾选即保存） |
| 5 | （对方侧） | 重新登录后按新角色与授权显示 |

- 老板侧耗时：约 3–5 分钟/人，跨 3 个界面（控制台 ×2 处 + 本站），
  且第 3 步在 Table Editor 里按 UUID 找人，易找错行；
- 断点风险：只发邀不改角色 → 对方以 staff 登录，看不到应看的汇总；
  只改角色忘勾业务授权 → 板块入口不渲染，对方以为「网站坏了」。

## 二、轻量方案（待邀请名单 + 一键对齐）

在本站 /members 老板区加「待邀请名单」，只做意向登记与事后对齐，
**发邀动作仍走 Supabase 控制台**（本站不持有 service-role 密钥，
这是既定红线，不因本方案改变）。

- 新表 `invite_intents`：email、intended_role（partner/staff，老板角色不开放
  意向登记，防误放大）、intended_scope、business_keys（意向授权板块）、
  status（pending → invited → aligned）、created_by/created_at；
  RLS：仅老板可读写，其余角色无策略（整表不可见）。
- 老板流程变为 3 步：
  1. 本站名单登记：邮箱 + 意向角色 + 意向授权（一次填完）；
  2. 控制台只剩「发邀」一个动作（可按名单逐个发）；
  3. 对方设密登录后，老板在名单点「一键对齐」：服务端以老板会话按邮箱
     精确匹配 auth 用户，写入 profiles.role/store_scope 与
     user_business_access，名单标 aligned。
- 可选二期「登录自动对齐」：用户首次登录时服务端按邮箱匹配 pending 意向
  自动应用，连第 3 步都省；风险更高（见下），列为二期再议。

## 三、工时估算

| 块 | 内容 | 估算 |
|----|------|------|
| 数据 | invite_intents 表 + RLS migration（老板执行一次 SQL） | 0.5 h |
| 界面 | /members 名单表单 + 列表 + 状态流转显示 | 1.5 h |
| 对齐 | 一键对齐服务端动作（匹配校验 + 写 profiles/授权 + 回执） | 1.0 h |
| 验收 | audit-staff 增断言（店员/合伙人名单不可见）+ /help 成员节同步 | 1.0 h |
| 合计 | | **约 4–5 h**（另老板执行 migration 约 5 分钟） |

## 四、风险

- **权限放大**：意向 role 只允许 partner/staff，owner 不走名单；
  一键对齐前界面二次确认目标邮箱与角色，防手滑。
- **对错人**：只按 auth.users 邮箱精确匹配对齐；查无此人或邮箱不一致
  直接报错不对齐，不做模糊匹配。
- **RLS**：invite_intents 仅老板策略；对齐写入走老板会话的现有
  profiles/授权表策略（老板全权），不新增任何绕过 RLS 的通道，
  不引入 service-role 密钥。
- **意向过期**：名单行长期 pending 会误导；加 30 天未对齐自动标「过期」
  显示（仅显示口径，不自动删数据）。
- **与现状并存**：上线后控制台流仍可用，名单只是登记与对齐层，
  回滚 = 删表与页面区块，不影响已建账号。

## 五、结论与推荐

- 推荐：立项一期（名单 + 一键对齐），二期自动对齐等一期跑顺、且真有
  第二个成员要邀请时再议——目前成员规模小，现状流的痛点是「步骤散」
  而非「量大」，一期已覆盖主要收益。
- 不推荐：为省发邀一步而引入 service-role 密钥或自建邮件发邀，
  违反零付费与密钥红线，收益不抵风险。
- 立项前置：老板裁定「做 / 不做」；做的话另下指令，本评估不自动开工。
