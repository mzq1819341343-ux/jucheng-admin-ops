## 逐项结果

1. **标记三态与文案**（数据只来自 fetch_logs，不写假时间）：
   - 真实模式库无记录（fromDb=false 且非演示）→ hasLogs=false →
     「数据刷新：暂无抓取记录（管道已备未启用）」✓ 与管道文档
     状态句一致；
   - 有日志、无 success、最新为 need_user_login → 同句 + 后缀
     「· 状态 待登录 need_user_login」✓；
   - 有 success → 「数据刷新：最近成功抓取 {时间} · 状态
     正常/待登录」✓。needLogin 判定 = 最新一条日志状态，口径与
     待启用配置.md 的会话失效停记规则一致。
2. **标记落点**：/status「数据源」节与爱回收仪表盘共用同一组件
   同一取数函数，无第二份实现 ✓。
3. **/status「10 月对账」卡**：状态标 need_user_login + 「抓数管道
   已备未启用，未建定时任务；本卡只展示状态，不写假进度」+
   一键启用恰 4 步（老板面板登录 → 按运行单首抓 → 对账校验 →
   启用双 cron 09:30 / 每月 3 日 10:00，Asia/Shanghai）——与
   fetch-pipeline/README.md 第 3 行状态句、待启用配置.md 启用
   条件与动作清单逐项对齐 ✓（字段级一致性另由 audit-status
   12 字段断言守，本轮 run-all 在内）。
4. **数据源表「爱回收自动抓取」行**：「待启用」标 + 策略句
   （增量 + 每月 3 日抓上月整月；会话过期只停下记录、不重试
   登录、不绕验证）✓ 与待启用配置.md 一致。
5. **抓取记录节角色口径**：整节仅 sensitive（老板/合伙人）渲染，
   店员整节不渲染、无占位卡 ✓（指令57 自扫 + 58 最严口径）；
   STATUS_LABEL 已含 need_user_login → 「待登录」（代码侧就绪；
   DB 侧状态约束放宽属 migration_009，未执行，见待老板清单）。
6. **一处呈现不一致（记录待裁定，本轮不改）**：抓取记录节只取
   `logs` 不消费 `fromDb`——真实模式下**若** fetch_logs 为空表，
   该节会渲染 FALLBACK_FETCH_LOGS 两行兜底（success「手动导入
   v3.3 汇总」/ pending「自动抓取未启用」，固定时间
   2026-10-26 18:00），而同页标记此时显示「暂无抓取记录」，
   两处对「有无记录」的呈现不一致。兜底两行所述均为真实事件
   （v3.3 汇总确曾手动导入、管道确未启用），不构成假进度；
   但真实模式下其来源（兜底/库记录）不可分辨。生产 fetch_logs
   是否为空表 Muse 侧无法核实（见卷首），故本项只记录：
   建议后续安静轮或 B 组启用轮裁定——记录节在 `!fromDb && !demo`
   时显式呈空态，与标记口径统一。本轮按 A6 口径未改代码。
