# 契约：员工草案占位与底薪同步

web 在员工保存成功、或底薪 PATCH 成功之后，立刻调用本仓这条写路径，给当月 `salary_realtime_draft` 补上占位行或改掉底薪。本仓没有 Next.js route。抓取任务骨架不在这里。

不写 migration。不改 `docs/fetch-pipeline/pipeline_config.json` 的 `UPLOAD` / `APPLY`（保持 false）。不灌 2026-10，也不连生产库做验收。

## 双闸

与 `scripts/apply_realtime_payroll_draft.py` 同一道环境闸，默认不写库。

| 条件 | 结果 |
|---|---|
| 未设置 `ALLOW_APPLY_REALTIME_DRAFT=true`，或没带 `--apply` / `apply=True` | dry-run，不连库 |
| 两者同时成立 | 才可以对 `salary_realtime_draft` 发 POST / PATCH |
| 目标月是 `2026-10` | 拒绝，退出码 2。双闸开齐也不写 |
| 目标月早于 `EFFECTIVE_FROM=2026-10` | 拒绝，退出码 2 |

生产禁盲开：没有第三道「生产放行」开关。`SUPABASE_URL`（或 `NEXT_PUBLIC_SUPABASE_URL`）和 `SUPABASE_SERVICE_ROLE_KEY` 只从环境读取，不进命令行、不进仓库。不要把生产项目的 service role 放进默认环境后随手加 `--apply`。

密钥只允许出现在 web 的服务端环境。浏览器、`NEXT_PUBLIC_` 变量、店员会话都不得持有 service role。

## 占位

在职保存成功后调用。只插入还没有草案的人。

| 列 | 写入 |
|---|---|
| `base_amount` | 本次 `employees.base_salary`。上门与门店都跟这个数，不因角色改成 0 |
| `door_amount` / `online_amount` / `store_amount` / `accessories_amount` | 0 |
| `subsidy_amount` / `bonus_amount` | 0（只在这行是新建时） |
| `deduction_amount` | 0 |
| `gross_amount` / `net_amount` | 与灌库脚本 `recompute_payable` 相同：五项业绩加补贴加奖金，实发再减扣款。新建时等于底薪 |
| `source` | `employee_placeholder`（`migration_011` 已有 `source` 列，不新增列） |
| `caliber` | `employee_placeholder\|pending_payroll\|base_follows_table`，有角色时再加 `work_role=` |
| `user_id` | 调用方带了 UUID 才写 |

冲突键是表上的 `(month, person_name)`。请求使用 PostgREST `Prefer: resolution=ignore-duplicates`，即 `ON CONFLICT DO NOTHING`。写库前若已读到该人该月的行，则直接跳过，不发插入。已有底薪、补贴、奖金、业绩都不改。

底薪后来变了要改数字时，不要再调占位。占位看到已有行会跳过。

## 底薪同步

底薪 PATCH 成功后调用，传入新的表底薪。

已有当月行：

- PATCH 只含 `base_amount`、`gross_amount`、`net_amount`、`as_of`、`updated_at`
- 不发送 `subsidy_amount`、`bonus_amount`、四项业绩、`deduction_amount`、`source`
- 应发按该行上保留的业绩、补贴、奖金、扣款，加上新底薪，走 `recompute_payable`

当月没有行：先按上面的占位插入（底薪已经是新值，业绩和补贴奖金为 0），再读回该行后写底薪。读回若已经有手填补贴或奖金（并发先写入），PATCH 仍不覆盖它们，应发把读回的值算进去。

非在职且当月没有行：不占位。非在职但已有行：只同步底薪。

## 命令行

```bash
python3 scripts/payroll/ensure_employee_placeholder.py \
  --person-name <姓名> --base-salary <表底薪> --work-role 上门 \
  --employment-status 在职 --month 2026-11

python3 scripts/payroll/sync_base_salary.py \
  --person-name <姓名> --base-salary <新底薪> --month 2026-11
```

真正写库再加环境变量和 `--apply`（仍拒绝 2026-10）：

```bash
ALLOW_APPLY_REALTIME_DRAFT=true \
SUPABASE_URL=https://<project>.supabase.co \
SUPABASE_SERVICE_ROLE_KEY=<service-role-key> \
python3 scripts/payroll/sync_base_salary.py \
  --person-name <姓名> --base-salary <新底薪> --month 2026-11 --apply
```

`--month` 省略时用 `pipeline_config.json` 的 `TIMEZONE`（缺省 Asia/Shanghai）日历当月。`--person-name` 与 `--user-id` 至少给一个。dry-run 不读库，所以还要 `--base-salary`。写库时如果缺姓名或缺底薪，用 service role GET `employees` 补齐，不写员工表。

`--employment-status` 省略、并且这次没有去读员工表时，按在职。web 应把刚保存的状态传进来。

## 给 web 复用的函数

`scripts/payroll/draft_employee_write.py`：

- `ensure_employee_placeholder(employee, month=None, *, now=None, env=None, apply=False, existing_reader=None, writer=None, employee_reader=None)`
- `sync_employee_base_salary(employee, month=None, *, patcher=None, 其余同上)`

`employee` 是字典：`person_name`（或 `name`）、`base_salary`、可选 `user_id`、`work_role`（或 `role`）、`employment_status`。

成功返回字典，`action` 为 `dry-run`、`skip`、`insert`、`patch`、`placeholder_then_patch`。`wrote` 表示有没有发出写请求。失败抛 `DraftWriteRejected`，`code` 即退出码。

web 仓是 Next。在服务端 Route Handler 或 server action 里，于员工写入已经成功之后调用，二选一：

1. 子进程跑上面的 CLI，环境变量放在服务端。
2. `importlib` 加载 `draft_employee_write.py`，调用同名函数。

鉴权假设：调用前，web 已经用老板（owner）会话完成了员工保存或底薪 PATCH。本函数不再校验用户 JWT。它只用 service role 写草案表。店员会话、浏览器、预览环境都不要调用。

建议顺序：

1. 在职保存成功 → `ensure_employee_placeholder`（或占位 CLI）。
2. 底薪 PATCH 成功 → `sync_employee_base_salary`（或同步 CLI），传入新底薪。

不要在底薪 PATCH 之后只调占位。已有行会被 DO NOTHING 留在旧底薪上。

## 退出码

| 码 | 含义 |
|---|---|
| 0 | dry-run，或写成功，或占位因已有行而 DO NOTHING |
| 2 | 2026-10 禁灌，或早于生效月 |
| 3 | 吕文飞或杨燕辉 |
| 4 | 非在职不占位（同步时：非在职且当月无行） |
| 1 | 其它。含缺底薪、双闸已开但没有库凭据、读不到补贴/奖金列、草案重名 |

读草案或写库失败时中止，不用 0 去填补贴和奖金。

## 冒烟

```bash
python3 scripts/payroll/smoke_employee_draft_write.py
```

不连库。覆盖三件事：已有行占位 DO NOTHING；底薪同步保留补贴和奖金；缺行先占位再写底薪。上门底薪断言为表内金额，不是 0。
