# 评估 · /status 对账卡「演示注入」回归预埋（指令64 A5，只评估不开发）

> 问题：是否现在就仿指令59 A2 的 `demo_targets` 模式，给 /status「10 月
> 对账」卡预埋一个演示注入开关（生产恒忽略），让卡翻转在 B2 真开发前
> 就能进回归实测？承《设计_对账卡自动翻转》§6 末行与 63-A7 演练记录。

## 结论：不预埋——注入开关与 B2 卡片推导同轮落地

现在单独预埋没有可测对象：**卡片今天根本不读日志**。翻转的状态推导
（先按 `source='aihuishou_auto_fetch'` 过滤再取最新，见设计 §2 与
63-A7 澄清）尚未开发，注入的日志只能影响刷新标记行与日志表——而这两处
的承重机制已在 63-A7 用仓库外小样实测全过（标记即时更新、日志表渲染
在位、§4 正则逐字解析含千分位、非模板回退不猜数）。预埋开关测不到卡，
只会多一条无人消费的死代码路径，且 B2 推导函数的签名/落点未定，开关
极可能要随推导返工。59-A2 的先例也是**注入与被测逻辑同轮落地**
（demo_targets 与复盘三分支同轮、同轮进回归），不是提前一轮预埋。

## 若 B2 同轮落地，注入面应这样开（设计先行，本轮只落字）

- **载体**：Cookie `demo_fetch_logs`，base64url 编码 JSON 数组，元素
  `{source, status, message, created_at}`；仅演示会话读取（判定与
  demo_targets 完全同构：分支挂在演示路径内，生产构建演示总开关关闭
  时 `getCurrentUser` 永不返回 demo 用户，分支恒不达）。
- **注入点**：卡片推导与刷新标记共用的取数路径（`getFetchLogs` 的
  演示分支），注入行置于日志列首（created_at 倒序口径下即「最新」），
  保证标记行、日志表、对账卡三处看到同一份日志——禁止只给卡片单开
  一条注入通道（会造出标记与卡片口径分叉，正是 63-A7 澄清要防的）。
- **校验口径**：仿 demo_targets 的逐字段过滤（source/status/message
  为字符串、created_at 可解析、条数上限 5 条），格式不对整份按未注入
  处理，不抛错、不渲染半截数据。
- **注入值纪律**：单量/分润只用虚构演练值（如 63-A7 的 412 单 /
  52,308.55 元），禁止把任何真实抓取数字写进注入样本或仓库。

## 生产恒忽略断言增补点（B2 同轮落地，本轮先登记）

1. audit-online 增 2 项：伪造 `demo_role` + `demo_fetch_logs` Cookie
   访问 `/status` 与 `/`，生产仍 307（与现有 demo_targets 注入断言同轨）。
2. audit-anchors（或 audit-status）增翻转用例：演示注入合模板的
   auto_fetch success 后——状态 tag 翻「已抓取」、单量/分润/抓取时间与
   注入值逐字一致、基线行与应抓区间行断言不变；非模板 message 注入
   走回退（只翻状态、数字位「明细见下方抓取日志」）；success 后再注入
   need_user_login 子态在位（不回退成未抓取）。此清单与 63-A7 演练
   记录《回归增补点》、设计 §8 合并执行，不重复造。
3. audit-staff /status 三角色轨复跑：卡翻转后三角色在位范围不变
   （状态卡非敏感、对账行仅老板、日志节店员不渲染）。

## 与 B2 的衔接方式

- B2 开工单里把「注入开关 + 上列断言」列为与卡片推导同一笔交付的
  组成部分（推导 commit → 注入 commit → 断言 commit），不拆到
  B2 之前的任何一轮预埋。
- 前置不变：A0''（migration_009 已执行）仍是 B2 前置——注入只解决
  演示态可测性，不解决真实模式 need_user_login 写不进约束的问题，
  两者不可互相冒充。
- 若 B 组长期不解锁、而后续某轮需要先行验证卡片渲染细节，可用
  63-A7 的仓库外小样法临时演练（改兜底副本、跑完即弃），不落仓、
  不留开关——本评估结论不因「想先看看效果」而改变。

## 明确不做（本轮）

- 不开发注入开关、不改 `lib/data.ts` / `app/status/page.tsx` 任何
  业务代码、不新增 Cookie 读取、不动回归断言。以上全部等 B2 同轮。
