# 设计 · /status「10 月对账」卡状态自动翻转（指令60 A6）

> **只设计不开发。** 触发条件：B1 10 月首抓真实完成（fetch_logs 出现第一条
> `aihuishou_auto_fetch` 的 success 记录）后，与后台接入（B2）一并开发。
> 在此之前页面保持现状（空态卡 + need_user_login），不写假进度。

## 1. 现状（设计基线，2026-10-27）

- 卡位置：`app/status/page.tsx`「10 月对账（待抓取）」节，三行字段：
  应抓区间 / 基线（不变） / 当前状态，外加「一键启用步骤」恰好 4 步
  （audit-status-consistency 逐字段守着这套文案，改卡必同步改该审计）。
- 卡渲染范围：三角色都在位（状态展示卡，非敏感数据，指令60 A2 已固化）；
  敏感角色另有登录恢复操作指引行，店员不渲染——翻转不改变此范围口径。
- 数据源 `fetch_logs`（supabase/schema.sql）：`source / status / message /
  created_at`，**无结构化的单量/分润列**；读取走 `lib/data.ts`
  `getFetchLogs()`（RLS：owner/partner 可读，店员经页面服务端渲染可见卡
  本身——卡数据不经 RLS 下发到客户端，维持现状服务端拼装）。
- 已有可复用逻辑：`getFetchRefreshMarker()` 已算出「最近 success 时间 /
  最新一条是否为 need_user_login / 是否有日志」，仪表盘与 /status 的
  「数据刷新」标记行在用；翻转判定必须复用同一份推导，禁止页面另算一套。
- 运行单约定（docs/fetch-pipeline/10月抓取运行单.md §5）：首抓成功后
  「在 Supabase fetch_logs 记一条 success（来源 aihuishou_auto_fetch，
  信息含 10 月单量与分润合计）」——这是翻转的唯一触发信号。

## 2. 状态机（三态，按最新相关日志判定）

只看 `source='aihuishou_auto_fetch'` 的日志（驾驶舱手动导入的
`aihuishou_cockpit_v3_3` success 不触发翻转）：

| 状态 | 判定（按 created_at 倒序看该 source 日志） | 卡「当前状态」渲染 |
|---|---|---|
| 待登录（现状） | 无该 source 日志，或最新一条为 need_user_login / pending 且从未有 success | 现行文案：`待登录 need_user_login` tag + 说明句 |
| 已抓取 | 最新一条为 success | `已抓取`（tag-ok）+ 单量/分润 + 抓取时间（见 §3 解析） |
| 已抓取·待重新登录 | 有过 success，但其后最新一条为 need_user_login（增量抓取会话失效） | `已抓取` + 单量/分润/时间保留，下加一行 `会话已失效，增量已停（need_user_login）`（tag-pending）；**不回退成从未抓取** |

failed / skipped 不改变状态（仍按上一条有效信号渲染），但「最近抓取 /
导入日志」节照常展示该行，老板可自行判断。

## 3. 字段映射（逐字段）

| 卡字段 | 待登录（现状） | 已抓取（翻转后） | 来源 |
|---|---|---|---|
| 标题 | 10 月对账（待抓取） | 10 月对账（已抓取） | 状态机 |
| 应抓区间 | 现行全文（完成时间区间 + 两店店号 + 对账单账单时间） | 不变（这是约定口径，不是结果） | 静态文案，与运行单 §1/§2 对位，audit-status 继续守 |
| 基线（不变） | 3,958 单 / 416,661.32 元全文 | **不变**（基线行永不随翻转改字） | 静态文案，锚点哨兵覆盖 |
| 当前状态 | 待登录 tag + 「管道已备未启用，未建定时任务」 | 已抓取 tag + 「订单 {单量} 单 / 分润 {金额} 元 · 抓取于 {created_at}」；待重新登录子态另加失效行 | 最新 success 日志的 message 解析（§4）+ created_at |
| 一键启用步骤（4 步） | 现行 4 步 | 换为「收尾确认」清单（见 §5 对位表，步数随之变化，audit-status 同步改断言）；cron 未建前清单末项仍显「待启用定时任务」 | 静态文案（按状态切换） |

月份参数化（设计决定点）：首版只服务 2026-10 首抓，标题与区间维持
写死 10 月；11 月起增量抓取常态化后，卡应滚动为「最近抓取月份」——
届时标题/区间由最新 success 日志 message 中的月份驱动，无 success 时
回退当前待抓月份。此滚动化不在首版范围，列为 B3 之后的跟进设计点。

## 4. message 约定与解析（单量/分润从哪来）

fetch_logs 无结构化数字列，首版从 message 解析。**写入侧先立约**
（运行单 §5 执行时按此模板写，A6 开发时同步把模板补进运行单）：

```
2026-10 抓取完成：订单 {单量} 单 / 分润 {金额} 元（asof 2026-10-25）
```

- 解析正则：`(\d{4}-\d{2}) 抓取完成：订单 ([\d,]+) 单 / 分润 ([\d,]+\.\d{2}) 元`，
  命中才渲染数字；金额按字符串原样展示，不在页面侧做浮点再算。
- 解析失败（老模板/手写日志）：状态仍翻「已抓取」+ 抓取时间，数字位
  渲染「明细见下方抓取日志」，**不猜数、不从别处拼数**。
- 中长期备选（不在首版）：给 fetch_logs 加 `detail jsonb` 结构化列
  （需新 migration），message 解析作为其回退。首版不为此单开迁移。

## 6. 空态与回退总表

| 情形 | 渲染 |
|---|---|
| 库里无任何 fetch_logs（真实模式 fromDb=false） | 现行卡原样（待登录）；刷新标记行维持「暂无抓取记录（管道已备未启用）」 |
| 只有 cockpit 手动导入 success | 不翻转（source 不符），卡维持待登录 |
| success 但 message 不合模板 | 已抓取 + 时间，数字位走「明细见下方抓取日志」 |
| 多条 success | 取 created_at 最新一条（推导方法与 marker 一致，但先按 source 过滤——marker 的 lastSuccessAt 为全源口径，卡片不得直接借用，指令63 A7 演练澄清） |
| success 后 need_user_login | 已抓取·待重新登录子态（§2），不丢已抓取信息 |
| 演示模式 | FALLBACK_FETCH_LOGS 无 auto_fetch success → 维持待登录，与现状一致；回归演示断言不新增假已抓取态（如需测翻转，另加 demo 注入开关，仿指令59 A2 的 demo_targets 模式，生产恒忽略） |

## 7. 开发前置核对（开工前逐项确认）

1. **status 约束**：schema.sql 基础约束为 `('success','failed','pending',
   'skipped')`，**不含 need_user_login**，而运行单 §6 要求失效时写入
   need_user_login、页面 STATUS_LABEL 也已有该值——否则首抓后的失效
   记录会写不进去。**现状更新（指令65 A6 复核）**：放宽迁移已于指令
   61-A2 落档为 `supabase/migration_009_fetch_logs_status.sql`（五值，
   文件头含三方对位表），与 008 的合并执行材料已备齐在
   docs/待老板_指令60材料.md（§〇连跑 + §四单份步骤与核对 SQL）；
   该前置的剩余动作只剩老板执行 009 并贴回核对回显——执行确认前，
   任何写入 need_user_login 的代码路径仍不得上线。
2. 运行单 §5 的 success 写入由谁执行（抓取流程人工写 SQL / 脚本写）：
   模板（§4）必须在 B1 执行时就按约写入，事后补写会造成翻转时间失真。
3. audit-status-consistency 的字段集随卡文案变更同步更新（标题、状态
   tag、步骤数），禁止先改卡后补审计。

## 8. 开发后验收设计（B1/B2 落地时执行）

- audit-status 增翻转用例（演示注入一条合模板的 auto_fetch success）：
  状态 tag、单量/分润字符串、抓取时间与注入值逐字一致；基线行断言不变。
- audit-anchors 增 10 月锚点（首抓实数，待 B1 后按实数锁定）。
- 三角色渲染轨不变：audit-staff /status 三轨断言继续全过（卡仍三角色
  在位，对账行/日志节范围不随翻转变化）。
- 线上点验：老板登录 /status 看翻转后卡与状态记录.md 时间互核一致。

## 9. 明确不做

- 不提前开发、不造假 success 日志、不改任何现有文案先行「占位」。
- 不把单量/分润写进 monthly_metrics 之外的第二套口径；卡上数字只是
  日志转述，经营数字仍以驾驶舱/后台核算为唯一来源。
- cron 是否已建不由本卡判定（B3 独立验收），卡只在收尾清单里转述状态。
