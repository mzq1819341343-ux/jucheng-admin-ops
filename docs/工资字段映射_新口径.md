# 工资字段映射 · 新口径（realtime 草案）

现行算数在 `scripts/payroll/realtime_payroll.py`。只产出本机草案，并可在双闸打开后 upsert `salary_realtime_draft`。不写 `salary_detail_import` / `salary_monthly`。`pipeline_config.json` 的 `UPLOAD` / `APPLY` 保持 false。

指令192 的旧定案（全员上门 50%、配件阶梯、四人硬排除）见 [`工资字段映射_192.md`](工资字段映射_192.md)，不再当现行应发。本文件不写实发数字，也不抄在职角色名单。名单样例只在 `scripts/payroll/active_roster.example.json`。

库内 `salary_rules.commission_rules` 已是 `accessories_pct: 30`（无 `accessories_tiers`）。脚本常量 `ACCESSORIES_PCT=0.30` 与之对齐。`schema.sql` / `migration_004` 里的阶梯种子是历史原文，本变更不改那些 SQL。已落库语句的归档是 `supabase/migration_012_employees.sql` 与 `supabase/migration_013_salary_rules_accessories_pct.sql`，不在本变更里执行。

## 拍板

| 点 | 落地 |
|---|---|
| A1 | 仅 `role=上门` 且取货方式=上门：分润 ×50% → `door`。`role=门店` 且取货方式=上门：不含券 → `online`（×1%），不进 `door`，不进门店阶梯基数，不进个人门店份额 |
| B1 | `ACCESSORIES_PCT=0.30`（实付）。`--accessories-input` 为独立 CSV/xlsx。缺文件或未传：配件=0，并写入 assumptions。禁止用旧机 191 列冒充 |
| C | 默认过渡 JSON。每人 `{name 或 person_name, role, base_salary?}`，`base_salary` 缺省 2000。不接受仅姓名列表。可选 `--roster-from=employees` / `ROSTER_SOURCE=employees`，只读 `employees` 里 `employment_status=在职` 的 `work_role` + `base_salary`。缺 `work_role` 拒绝出草案。本脚本不写该表 |
| D | 代码不再启用 `accessories_tiers`。meta / assumptions 写 `accessories_pct=30`。改规则的 SQL 已在库侧完成，本变更只归档、不执行 |

硬排除 `HARD_EXCLUDED = ("吕文飞", "杨燕辉")`。张浩冉、张静怡已移出硬排除；他们是否计薪只看名单里的 role。出现在计薪名单中的硬排除人员：退出码 3，不写输出。

## 名单

```json
{
  "active": [
    {"name": "示例甲", "role": "上门", "base_salary": 2000},
    {"person_name": "示例乙", "role": "门店"}
  ],
  "excluded": [{"person": "示例丙", "reason": "离职"}]
}
```

- `role` 只能是 `上门` 或 `门店`。缺 role、空名单、仅姓名字符串：退出码 4，不出草案，不默认角色。
- `base_salary` 省略，或等于 2000：基础 1000 + 全勤 500 + 拉新 500。其它非负金额整笔记入 `basic`，全勤与拉新为 0。
- 在职但当月没有订单的人仍出一行底薪。
- `--base-exceptions` 仍是非现行覆盖，缺省不读。
- `--roster-from=employees` 与 `--active-roster` 同时给出，或与 `ROSTER_SOURCE` 冲突：拒绝出草案。
- employees 读取列：`person_name, work_role, base_salary, employment_status, user_id`。只取在职。离职跳过。`user_id` 不写入草案 JSON。无凭据或 HTTP 失败则拒绝，不改用空名单。

## 订单怎么进各项

人员归属仍是「门店验货人」。金额仍是 Decimal。空的不含券、空的分润、空的实付都不补值。

| 条件 | online ×1% | door ×50% | 门店阶梯基数 |
|---|---|---|---|
| role=上门，取货=上门，来源≠门店 | 不含券 | 分润 | 不含券 |
| role=上门，取货=上门，来源=门店 | 否 | 分润 | 不含券 |
| role=上门，取货≠上门，来源≠门店 | 不含券 | 否 | 不含券 |
| role=上门，取货≠上门，来源=门店 | 否 | 否 | 不含券 |
| role=门店，取货=上门（不论来源） | 不含券 | 否 | 否 |
| role=门店，取货≠上门，来源≠门店 | 不含券 | 否 | 不含券 |
| role=门店，取货≠上门，来源=门店 | 否 | 否 | 不含券 |
| 不在名单 | 否 | 否 | 不含券仍进全店定档 |

`ONLINE_MODE` 仍是 `source_not_门店`。扩展说明写在 `meta.caliber.online_mode=source_not_门店+store_role_door_as_online`。门店来源的上门单不会因为「来源≠门店」再加一次。

门店档位：全店阶梯基数 ≥60000 → 4%，≥30000 → 3%，否则 0。个人门店提成 = Σ（个人在该店的阶梯基数 × 该店档位）。`meta.store_tier_reference` 里的 `base_amt_excl_coupon` 是剔掉「门店角色上门单」之后的基数，`store_role_door_excluded_amt` 是被剔出的金额。分润基数仍只作对照。

`gross = base + door + online + store + accessories`。

## 配件（G1）

191 旧机订单没有配件列，也没有实付列。脚本不读订单上的金额当配件。

`--accessories-input` 要有：

- 人：`归属人` 或 `销售人`（不认「门店验货人」）
- 金额：`实付金额`
- 日期：`完成时间` / `销售时间` / `日期` / `完成日期`（只取 `--month`）

表头若含订单列（门店验货人、取货方式、分润金额、订单金额、不含券、结算金额、来源类型），直接拒绝。人不在名单上的实付不计入，只在 meta 里记人数。未传文件或路径不存在：`accessories=0`，`caliber.accessories_pct=30|source=none`，assumptions 写明缺源。

## 灌库

`scripts/apply_realtime_payroll_draft.py` 仍是默认 dry-run。写库要 `ALLOW_APPLY_REALTIME_DRAFT=true` 和 `--apply` 同时成立，且只 upsert `salary_realtime_draft`。表上没有 `role` 列，所以角色不进 UPSERT；`base_salary` → `base_amount`，四项提成与 `gross` 沿用原列。`meta.caliber` 有内容时追加进 `caliber` 文本。硬排除断言仍在，用的是收窄后的两人。

## 退出码

| 码 | 含义 |
|---|---|
| 0 | 已写出本机草案（或 apply 的 dry-run / 成功 upsert） |
| 2 | 月份早于 `EFFECTIVE_FROM=2026-10` |
| 3 | 计薪名单含吕文飞或杨燕辉 |
| 4 | 缺名单、缺 role、仅姓名列表、名单来源冲突、employees 在职行缺 work_role |
| 1 | 其它（含用 191 列冒充配件、employees 连不上） |

拒绝出草案时不创建 `--out-dir` 里的 payroll 文件。
