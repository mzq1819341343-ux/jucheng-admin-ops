## 尖锐自检（开工前三问）

1. **只跑本地 LCP 轮次而不改 iad1，为什么是浪费老板时间？**
本地 LCP 是在 VM 上对着演示兜底数据测的渲染耗时（实测各页 HTML 本地 TTFB 仅 10–20ms），它测不到老板的真实瓶颈：函数在弗吉尼亚、库在新加坡、人在中国，每次取数先跨一趟太平洋。老板感知的 1.2–2.0s 里，本地渲染只占个位数百分比。再跑七十轮，数字再漂亮，老板在石河子打开手机还是等那一趟跨洋往返——测的不是他的卡。
2. **卡顿主因判读与证据链？**
主因是**「函数区域错位 × 服务端串行取数」的乘积**，不是单点：① 响应头 `x-vercel-id` 改前两域均为 iad1 前缀，函数默认在美东执行；② Supabase 在新加坡（见 A2），VM（纽约出口）实测其 REST 端点新建连接 TTFB 0.43–0.56s（热 RTT 约 200ms 量级）；③ 代码审计数出老板路径的串行往返：总览约 11 次、驾驶舱约 13 次（见 A3 表）——11 次 × 约 200ms ≈ 2.2s，与老板 Mac 实测 1.2–2.0s 同量级、互相印证。前端体积是次因（首屏 845KB JS 含 259KB 与首屏无关的 supabase-js，见 A4），边缘缓存不是主因（/login 已是边缘 HIT 仍慢在跨洋段）。
3. **漏了什么？哪条路径老板天天点却没测？**
① **中间件（proxy.ts）每次请求先打一次 Supabase Auth 校验**——所有页面、所有静态资源之外的请求都躲不开，此前 perf 轮次从未单独计量它；132 区域化后它随函数区/边缘就近而受益，但其 RTT 仍在关键路径上（133 继续盯，含 getClaims 本地验签的评估，但不动 auth 语义）。② **手机端点开后的「写操作」往返**（报销提交、目标保存等 Server 端写库 + router.refresh 重取整页）此前只测读路径；乐观更新已缓解感知，但 refresh 的重取仍走全链，133 按页拆。③ **冷启动**：Hobby 函数闲置后首访有冷启动叠加，老板「早上第一次打开最卡」与此吻合，本轮无独立冷启样本，133 补测。
